# Project installation and application

Design of **how the "macOS-style" layer is installed and applied**. Written on
facts verified on this machine (CachyOS, KDE Plasma 6, Wayland), not on assumptions.

- Date: 13/10/2025
- Analysis it derives from: [ANALYSIS.md](ANALYSIS.md) · Evidence: [VERIFICATION-ANNEX.md](VERIFICATION-ANNEX.md)

## 1. Main finding: your system already solved the hard problem

Point A2 of the analysis ("the QStyle does not activate on its own") **was correct as a warning,
but it has a better solution than I assumed**, and the proof is on your own machine:

```
~/.config/kdeglobals
    [KDE]
    Line 144:  widgetStyle=kvantum

/usr/lib/qt6/plugins/styles/
    breeze6.so
    libkvantum.so
```

**Kvantum is a third-party QStyle, installed from the system, and it is active in your
session.** That demonstrates the whole mechanism, with no need for `QT_STYLE_OVERRIDE`:

1. The style's `.so` lives in the Qt 6 style plugins directory.
2. The style is selected with **a single key** in `kdeglobals`: `[KDE] widgetStyle=`.
3. Plasma 6 respects it and applies it to apps that start afterwards.

Operational conclusion: **there is no need to force the style per process.** The installer
writes a configuration key, just as Kvantum did. This removes at a stroke the
launcher mechanism and the `QT_STYLE_OVERRIDE` I feared in the analysis, and makes the
project considerably more viable.

> Verified nuance: Plasma 6 **does** keep the "Application Style" selector.
> On this machine `kcm_style.so` exists in
> `/usr/lib/qt6/plugins/plasma/kcms/systemsettings/`, and its internal strings contain
> `widgetStyle`, `WidgetStyle`, `widgetStyleChanged` and `defaultWidgetStyleValue`. In other
> words: **the KCM writes exactly the same `kdeglobals` key that the
> installer is going to write.** Therefore the installer does the same as the graphical interface, without
> depending on it. That correspondence is what makes the design robust.
>
> Two warnings that come out of those same strings:
> - There is a property `isWidgetStyleImmutable`. If a distro or an environment marks the
>   style as immutable, `widgetStyle` is ignored. `preflight` must check it, or
>   step 4 will fail silently and look like a QStyle bug.
> - There is `widgetStyleChanged`: if writing `kdeglobals` were not enough for already
>   open apps to find out, the notification can be fired over D-Bus. In practice it is enough
>   to restart the apps, because the style is read when each process starts.

**Second finding:** `~/.config/gtk-3.0/` and `~/.config/gtk-4.0/` **are already managed
by `kde-gtk-config`** (`window_decorations.css` and `colors.css` are generated by KDE). And you have
`gtk-font-name=Noto Sans, 10` and `gtk-theme-name=Breeze` in `settings.ini`. That is: the
typographic axis you asked to include **already has an existing application point** that must
be respected, not invented.

**Third finding:** `~/.local/share/flatpak/overrides/` already exists with 7 apps. The way to
inject environment into Flatpak is `flatpak override --user --env=...`, a standard and
supported mechanism, not patching.

## 2. Installer design principles

| Principle | How it is met |
|---|---|
| **No sudo** | Everything under `$HOME`. The installer never invokes `sudo` nor writes outside `~` |
| **Idempotent** | Running it twice with the same commit produces **the same content**. Build in a temporary directory + atomic `mv`, never in-place writing |
| **Auditable** | `--dry-run` prints the exact list of operations and differences, without touching anything |
| **Reversible** | Dated backup of every file touched, manifest in `~/.local/state/`, and `rollback` that restores the previous state |
| **No surprises** | `preflight` validates the environment **before** touching anything |
| **Portable** | XDG paths (`$XDG_CONFIG_HOME`, `$XDG_DATA_HOME`, `$XDG_STATE_HOME`), not fixed paths. `~/.local` and `~/Documents` are still valid by default, but they are not hardcoded |

Change with respect to the brief: the brief fixes "everything in `~/.local` and `~/Documents`". It is kept
as the default result, but **the code uses XDG variables** — it is free and it is what
makes the "installer for changing distro" actually work.

About the token format: the brief proposes `tokens.json`. I recommend **TOML or
`key=value`** instead. The reason is concrete: the tokens are meant to be **read and
diffed** in reviews, and a TOML produces one-line diffs per token while
JSON produces diffs with commas, braces and reindentation. It is the difference between auditing and
guessing. (`tokens.json` can be generated from the TOML if some tool demands it:
the TOML is the source, the JSON a derivative.)

And what is **not** in the repo, because it is system state:

```

└── version             <- installed version (to compare with the repo)
```

## 4. Real installation destinations

Paths verified on this machine. The installer detects `lib` vs `lib64` instead of
assuming it.

| Layer | What is installed | Destination | How it is activated |
|---|---|---|---|
| **QStyle** | `kdemacos.so` | `~/.local/lib/qt6/plugins/styles/` | `kwriteconfig6 --file kdeglobals --group KDE --key widgetStyle kdemacos` |
| **Colors** | `KdeMacos.colors` (or two: light/dark) | `~/.local/share/color-schemes/` | `--group General --key ColorScheme` + `ColorSchemeHash` |
| **Typography** | Font files (after license validation) | `~/.local/share/fonts/` | `--key font` (and `fixed`), + `fc-cache -f` |
| **KWin: corners** | effect `.so` | `~/.local/lib/qt6/plugins/kwin/effects/` | `kwriteconfig6 --file kwinrc --group Plugins --key esquinasEnabled true` |
| **KWin: material** | same effect | same | same |
| **GTK3** | `kde-macos.css` + import | `~/.local/share/themes/kde-macos/gtk-3.0/` | **via `kde-gtk-config`**, not by writing `gtk-3.0/gtk.css` by hand |
| **GTK4** | `kde-macos.css` | `~/.local/share/themes/kde-macos/gtk-4.0/` | the user's `gtk-4.0/gtk.css` (respecting the `@import` that already exists) |
| **Flatpak** | environment variable | `~/.local/share/flatpak/overrides/<app>` | `flatpak override --user --env=GTK_THEME=kde-macos <app>` |
| **Electron** | its own `.desktop` | `~/.local/share/applications/` | per-app flags; **list of accepted exceptions** |

### Critical detail about GTK

On your system, `~/.config/gtk-3.0/gtk.css` contains exactly `@import 'colors.css';` —
that is, **`kde-gtk-config` already owns that file**. If the installer writes there
directly, the next time you open *System Settings → Appearance → GNOME/GTK
Style* KDE will overwrite it and you will lose the work.

Design rule: **the installer does not own the `kde-gtk-config` files, it hooks into
them.** Specifically, it installs the theme in `~/.local/share/themes/` and then lets KDE
select it through `kde-gtk-config`, instead of writing CSS by hand in `~/.config`.
This is the kind of detail that decides whether the project survives the user's next
configuration session.

## 5. The installer: `install.sh`

A single entry point with subcommands. No having to remember ten scripts.

```bash
./install.sh preflight     # is the environment as I expect? Does NOT touch anything
./install.sh plan          # --dry-run: lists operations and diffs. Does NOT touch anything
./install.sh instalar      # applies (requires a clean plan)
./install.sh verificar     # regression captures + functional checks
./install.sh estado        # what is installed, version, differences with the repo
./install.sh rollback      # restores the last backup (one command)
./install.sh desinstalar   # reverts EVERYTHING and leaves the system as it was
```

### `preflight` — what is validated before touching anything

```
1. Environment: $XDG_SESSION_TYPE=wayland, $XDG_CURRENT_DESKTOP=KDE, KDE_SESSION_VERSION=6
2. Tools:      kwriteconfig6, kreadconfig6, fc-cache, qdbus6
   -> verified: all four present on this machine
3. Qt:         locate the style plugins directory and CHECK that
              ~/.local/lib/qt6/plugins is a real Qt6 search path
              (if it is not -> write QT_PLUGIN_PATH in ~/.config/environment.d/)
4. lib vs lib64: detect which one this system uses
5. Conflict:  does widgetStyle already exist? which one? -> it is saved in the manifest
6. Collision: does ~/.local/share/themes/<nombre> exist? whose is it?
7. Budget:    space and write permissions in each destination
8. Production: cmake, ninja, headers Qt6 -> ONLY if the QStyle is going to be compiled
```

Point 3 is the only one that **must be resolved empirically** before writing the
final installer: check with `QT_DEBUG_PLUGINS=1` whether Qt6 scans the user
directory. If it does not, the `QT_PLUGIN_PATH` line in `~/.config/environment.d/` is the
solution, and it is one line.

### `plan` — readable audit

Expected output, in this exact format:

```
[CREATE]     ~/.local/share/color-schemes/KdeMacos.colors          (new)
[CREATE]     ~/.local/lib/qt6/plugins/styles/kdemacos.so           (new)
[MODIFY]     ~/.config/kdeglobals
             [KDE] widgetStyle: kvantum -> kdemacos
             [General] ColorScheme: Ant-Dark -> KdeMacos
             (backup -> ~/.local/state/kde-macos/backups/20251013-174500/kdeglobals)
[NO CHANGES] ~/.config/gtk-4.0/gtk.css
[EXCEPTION]  not touched: VS Code (Electron, its own CSD)
```

A diff per key, with the previous and the new value. This is what makes the script
"auditable" for real: not declarative in the abstract, but **reviewable before applying**.

### Idempotence, concretely

The typical mistake is "copy the files and that's it". The correct way:

```
1. Build EVERYTHING in $XDG_CACHE_HOME/kde-macos/build-<hash-de-contenido>/
2. Compare with what is installed by hash
3. If anything changes: backup + atomic mv (never a partial in-place write)
4. Regenerate the manifest
```

Measurable consequence: running `install.sh instalar` twice with the same commit leaves
`manifest.tsv` **identical**. That is the idempotence test, and it can be automated.

### Damage containment

The real risk is not the QStyle (it applies **per process**: a bad app is closed and that's it),
it is `kdeglobals`, which all KDE/Qt processes share. Mitigations, in order:

1. Write `kdeglobals` **only with `kwriteconfig6`**, never with `sed` or by rewriting the
   file. `kwriteconfig6` respects the format and avoids corrupting it.
2. Dated `backup` of `kdeglobals` **and** `kwinrc` before any change.
3. `rollback` = restore backup + `kwriteconfig6` back. One command.
4. **Escape route without a GUI**: if something leaves the Qt apps unusable, switch to a TTY
   (`Ctrl+Alt+F3`), log in and run `./install.sh rollback` or `desinstalar`
   from text. This works even if there is not a single usable dialog. It is the insurance that
   makes it acceptable to test the widget style on the whole system.

## 6. Staged deployment (this is the "how it is applied")

Never apply the four layers at once. The order is designed so that each stage
**validates** the next and so that you know exactly what broke if something breaks.

```
STAGE 0 · preflight + plan
    installs nothing. Point 3 (Qt6 plugin paths) is resolved here.

STAGE 1 · A SINGLE PROCESS (the decisive test)
    QT_STYLE_OVERRIDE=kdemacos kate &
    -> verify: it does not crash, the controls are drawn, the metrics are correct
    -> if it fails here, NOTHING in the system breaks. Cost of failure: zero.

STAGE 2 · COLORS + TYPOGRAPHY (low risk, high impact)
    color scheme + fonts. Both are reversible with rollback and do not depend
    on the QStyle being finished.
    -> this already delivers visible value with the QStyle half done.

STAGE 3 · KWIN (corners + darkened border)
    KWin effect. It unifies the apps that will never respect the QStyle.
    It only affects compositing: a bad effect is disabled and that's it.

STAGE 4 · QSTYLE ON THE SYSTEM (the only step with global scope)
    widgetStyle=kdemacos in kdeglobals.
    -> preceded by `verificar` and followed by `verificar`.

STAGE 5 · GTK + FLATPAK (realistic expectations, list of exceptions)
```

Stage 1 is the jewel of the design: **it gives you 100 % of the information about the biggest
risk with 0 % of the risk**. It is an `&` on one line.

## 8. Requirements the installer CANNOT satisfy

This answers the "no sudo, no AUR" nuance in the analysis (§4.3), specifically:

| Need | Installer? | Status on this machine |
|---|---|---|
| Compiling the QStyle and the KWin effect | **No** — it is your development environment | `gcc` ✅, `g++` ✅, `pkg-config` ✅, headers Qt6 ✅, **`cmake` ❌**, **`ninja` ❌** |
| Running the installer | Yes, with what is already there | Everything present ✅ |
| Loading the QStyle into the apps | Yes | `kwriteconfig6` ✅ |

`cmake` and `ninja` are **not installed** on this machine. They are needed to compile the
QStyle (step 5 of the plan) and they are installed with `pacman`, which requires sudo and touches the system.

**Distinction that is best fixed in the brief:**

```
The DELIVERABLE does not use sudo or AUR.  <- true, and it must be kept that way
DEVELOPMENT does install tools.           <- also true, and it does not contradict the above
```

Writing it as "the installer does not use sudo" instead of "no sudo" avoids getting stupidly
blocked in the compilation phase without weakening the restriction that really matters:
that the result is reproducible on any distro without privileges.

## 9. Typography, applied

Your observation that typography deserves to be included is made concrete like this:

1. **Choice**: `Inter` as the UI family (SIL OFL license, redistributable). For
   headings with an optical axis, `Inter Display`. Monospace: `JetBrains Mono` or
   `IBM Plex Mono`. **SF Pro is not redistributed** (Apple license) — it is documented as
   the user's choice, it is not packaged.
2. **New tokens** in `tokens.toml` (the axis the brief was missing):

```toml
[tipografia]
familia_ui       = "Inter"
familia_titulos  = "Inter Display"
familia_mono     = "JetBrains Mono"
tamano_ui        = 10        # in points, as KDE expects them
tamano_barra     = 11
interlineado_escala = 1.15   # the macOS "air" is not the size, it is the line spacing
espaciado_control   = 8      # internal padding: what almost nobody adjusts and is most noticed
```

3. **Application point**: `kdeglobals` (`font`, `fixed`) for Qt/KDE, and
   `~/.config/gtk-4.0/settings.ini` (`gtk-font-name`) for GTK — where today you have
   `Noto Sans, 10`. A family change goes through the generator, not through three places by hand.
4. **Verification**: `fc-match "Inter"` must resolve to the installed font and not to a
   silent fallback to DejaVu. It is a one-line check that is added to `preflight`, and
   it catches the most common failure ("installed" font that fontconfig ignores).

## 10. Summary

**How it is installed:** a single `install.sh` script with subcommands, no sudo, idempotent,
with `plan` to audit beforehand and `rollback`/`desinstalar` to revert. It builds in
cache, compares by hash and does an atomic `mv`. All the state stays in
`~/.local/state/kde-macos/`.

**How it is applied:** the central finding is that **Plasma 6 accepts a third-party QStyle
through a single key in `kdeglobals`** — your Kvantum already proves it. That turns the
main risk of the analysis (A2) into one line of configuration. It is applied in five
stages, starting with a single process with `QT_STYLE_OVERRIDE` (zero risk) and going up
to global scope, with an escape route through a TTY.

**What changes in the brief as a result of this:**

1. "The QStyle does not activate on its own" → **it is activated with `widgetStyle` in `kdeglobals`**, and there is
   a precedent working on this machine. A2 is resolved for the better.
2. Add the **typographic axis** to the token system (valid point, confirmed).
3. **Do not write to the files owned by `kde-gtk-config`**: hook into its mechanism.
4. Rewrite "no sudo" as **"the installer does not use sudo"**.
5. Use **TOML** for the tokens, not JSON, for auditability.
6. Include **stage 1, the single-process test**, as a mandatory step before
   global deployment.
